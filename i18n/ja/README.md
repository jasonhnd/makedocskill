## なぜこのスキルが存在するのか

多くの AI ツールは同じ方法で企業ドキュメントを生成します。テキストをテーマに流し込んで「完了」とする。見出しにブランドカラーの付いた箇条書きの壁 —— しかし数値はソースと突き合わせて検証されておらず、日本語は取締役会レベルではなくカジュアルで、章は改ページされず、誰も実際に開いていない書き出された PDF は崩れています。

問題は生成速度ではありません。問題は、**ファイルが書き出される前に、編集判断が行われていない**ことです。

上場企業 CFO オフィスの取締役会ドキュメント編集者は、まず Word を開きません。先にソースを読み、それが本当に取締役会資料なのか、IR 資料なのか、CFO 提案なのかを見極め、監査人が突くであろう弱い論点に挑戦し、すべての数値をソースにロックし、言語を整え、最後にレイアウトします。ドキュメントは最後の一歩であり、最初の一歩ではありません。

make-doc-skill も同じ方法で動作します。**Brain -> Router -> Canvas** パイプラインにより、判断とレンダリングを分離します。

- **Brain** は編集者でありドメインアナリストです。本当の成果物を推論し、構造を再構築し、三次元の専門家スパーリング（仮説への挑戦、死角の補完、視点の再構成）を実行し、用語を統一し、崩れた階層とトーンを修正します。これが **Codex インテリジェンス層** —— 説得力あるすべての取締役会資料の背後にある実行エンジンです。
- **Router** はドキュメントアーキテクトです。成果物タイプを出力ファミリー —— 正式 DOCX、日中バイリンガル分割ファイル、16:9 デック、または HTML —— にマッピングし、セクションごとのコンポジション計画を作成し、レンダラーとテンプレートを選択します。
- **Canvas** はレンダラーであり組版者です。企業ブランドトークンとレイアウトルールを適用し、DOCX/HTML をレンダリングし、PDF を書き出し、QA を実行します。編集的な判断は**一切しません**。

トークンはデザインの記憶です。Brain の判断は実行エンジンです。**深度はステップ数ではなく、判断の鋭さから生まれます** —— 取締役会ドキュメントが説得力を持つのは、Canvas がカラーテーマを適用したからではなく、Brain が資料を正しく読み、それを再構築したからです。

結果：CFO オフィスが制作したように読める正式な Word/PDF 取締役会資料と IR/CFO デック、監査に耐える数値。すべて単一の Claude Code スキルから。

## アーキテクチャ

```
┌──────────────────────────────────────────────────────────────┐
│                      make-doc-skill v4                       │
│                  企業ドキュメントジェネレーター              │
│                                                              │
│   ┌──────────┐     ┌──────────┐     ┌──────────────────┐    │
│   │  Brain    │────>│  Router  │────>│     Canvas       │    │
│   │          │     │          │     │                  │    │
│   │ 編集者 /  │     │ ドキュメ │     │ レンダラー /     │    │
│   │ アナリスト│     │ ント設計 │     │ 組版者           │    │
│   │ スパーリ  │     │ 出力ファ │     │ DOCX / HTML      │    │
```

**核心原則**：深度はステップ数ではなく、判断の鋭さから生まれる。

3 層は設計上分離されています。Brain が大幅に書き換えても、Canvas は分析的な散文をドキュメントに流し込みません —— Router がそれをドキュメント構造（章、テーブル、コールアウト、図）への翻訳を強制します。トークンはデザインの記憶、Brain の判断は実行エンジンです。

## 2 つのモード —— Quick Mode / Full Mode

| モード | トリガー | フロー |
|--------|---------|------|
| **Quick Mode** | 既存の Word/PDF/テキストを投入し、プロジェクト設定なしで素早く仕上げたい | 入力検出 -> 抽出 -> 本当の成果物を推論 -> 企業トークン適用（または妥当なデフォルト）-> Brain 軽量パス -> レンダリング -> PDF 書き出し -> パス報告 |
| **Full Mode** | 取締役会/IR 資料、バイリンガル納品、または「ドキュメントをきちんと作る」 | 中間ファイルとユーザーチェックポイント付きの 8 ステップ監査パイプライン |

Quick Mode はスパーリングの深さを速度と引き換えにしますが、**数値忠実度と言語ロックのチェックは依然として実行し、決して捏造しません**。Quick 出力後、Full Mode へのアップグレードを提案します（正規化したソースを保持し、トークン・スパーリング・レビューを追加）。

## 深度制御（S / M / L / XL）

深度は Brain の分析の強さと QA の厳格さを制御します。数値忠実度や言語ロックが適用されるかどうかは制御**しません** —— これらは常に適用されます。

| | S | M | L | XL |
|--|---|---|---|-----|
| **ユースケース** | 1 ページのエグゼクティブサマリー / メモ | 標準提案 / 説明 | 完全な取締役会資料 / IR ドキュメント | 包括的な取締役会資料 + 付録 |
| **セクション数** | 3-5 | 5-8 | 8-12 | 12+ |
| **Brain 深度** | コア結論 + アクション | + エビデンス評価 | + 説明フレームワーク + 代替案 | + 多視点レビュー + 極限テスト |
| **スパーリング回数** | 0-1 | 1-2 | 2-3 | 3+ |
| **図の数** | 0-1 | 1-2 | 2-4 | 4+ |
| **QA 厳格度** | 出力存在 + フォント + パス | + 目次 + ページ付け | + バイリンガル整合 + 図 QA | 完全な品質ゲート + ビジュアルコンタクトシート |
| **デックスライド数（16:9 の場合）** | 3-6 | 6-10 | 10-15 | 15+ |

ユーザーがサイズを指定しない場合、成果物から推論します：メモは S、CFO 提案は M-L、付録付きの完全な取締役会資料は L-XL。

## Codex インテリジェンス層

デザイントークンだけでは不十分です。カラー、フォント、サイズ、スペーシングは定義しますが —— ドキュメントが説得力を持つか、読みやすいか、上場企業のコンテキストに適しているかは決めません。この層が、パイプラインにおける Brain **そのもの**です。

毎回実行されます。

- **本当の成果物を推論する。** 字面のファイルタイプだけではなく。「Word/PDF」のリクエストは、取締役会資料、IR 資料、CFO 提案、業務説明、対外デックのいずれかかもしれません。
- **設計前に既存ドキュメントを読む。** テキストだけでなく弱点も抽出：崩れた階層、悪い改行、過密なテーブル、不安定な図、誤った配置、悪いページリズム、ミスマッチなトーン。
- **曖昧なブランド方向を具体的なトークンに変換する。**「青を使わず、当社のコーポレートカラーで」は、実際の体系（例：赤/グレー）を定義し、見出し・テーブル・リンク・図・チャートから誤用された青を除去することを意味します。
- **編集判断を下す。** 見出しを書き換え、過剰な段落を分割し、用語を統一し、セクション順序を引き締めます。
- **本物の出力サーフェスを検証する。** DOCX は書き出された PDF が読めるまで完了ではなく、デックはブラウザレンダリングと PDF 書き出しの両方が正しく見えるまで完了ではありません。
- **ユーザーのファイル規律を守る。** ソースファイルを上書きしない。最終ファイルは納品フォルダ（デフォルト `~/Downloads`）へ。

要するに：トークンはデザインの記憶、Codex 流の判断は実行エンジン。スキルは検査し、決定し、再構築し、検証し、納品すべきです。

## スパーリング、アンカリング、禁止ルール

これが Codex インテリジェンス層を、単なる「LLM の書き換え」ではなく信頼できるものにしています。スパーリングは M 深度以上で実行、アンカリングと禁止ルールは Quick Mode を含む全深度で実行します。

### 三次元の専門家追問（Step 4）

| 次元 | ゴール | 強制 |
|------|-------|------|
| **仮説への挑戦** | コア主張を検証 | 主張は擁護可能か？一次データか断言か？取締役や監査人が出す最強の反論は？ |
| **死角の補完** | 欠けた次元を埋める | 何が欠けているか —— ダウンサイド、リスク、希薄化、規制、税務、先例、タイムライン？ |
| **視点の再構成** | より良いフレーミングを提示 | リスク優先 / 比較優先 / タイムライン優先のフレーミングはこの聴衆により適しているか？ |

### アンカリングルール（上場企業資料では譲れない）

- **数値忠実度** —— 数値はソースのまま使用。丸めず、捏造しない。通貨、単位、会計期間は正確に。
- **マテリアルアンカリング** —— ソースが支持する内容のみ記載。欠損データは `[DATA_GAP]` をマーク。
- **ソース帰属** —— 補足/背景知識は `[Supplemental]` をマーク。
- **言語ロック** —— 出力言語が決まったら全チェーンがそれに従う。引用は原文言語を保持。
- **ピラミッド + MECE** —— 結論が先、次に論拠、その後データ。セクションは相互排他かつ完全網羅。

### 禁止出力

- 結論を避けるための曖昧なフィラーを使わない。
- 判断を回避しない —— 資料が推奨を支持するなら、明言する。
- 数値、引用、法律/税務/会計の結論を捏造しない。未検証の記述は草案/仮定としてマーク。
- 因果説明のない現象列挙をしない。
- 弱いソースの表面的な言い換えをしない —— 再構築する。

## パイプライン —— Full Mode 8 ステップ

各ステップはプロジェクトフォルダにレビュー可能なファイルを書き込み、チェックポイントで終わります：**続行 / このステップをやり直す / デフォルトでスキップ / レンダリングへジャンプ**。スキップ時は妥当な企業トークンのデフォルトを適用します。反復は旧ファイルを `_history/v[N]/` にアーカイブし、プロジェクトルートには常に最新版を保持します。

| ステップ | アクション | 出力 |
|---------|----------|------|
| **1** | 企業トークン | `01_company_tokens.md`（ブランド / 言語 / docx / スライドトークン） |
| **2** | ドキュメントブリーフ | `02_document_brief.md`（成果物タイプ、聴衆、言語モード、深度、出力、納品フォルダ） |
| **3** | ソース正規化 | `03_source_normalized.md`（Word/PDF/テキスト -> 構造化 MD/YAML、引用を保持、`[DATA_GAP]` をマーク） |
| **4** | Codex スパーリング | `04_codex_sparring.md`（三次元追問、弱点リスト、編集判断） |
| **5** | コンポジション計画 | `05_composition_plan.md`（セクション設計図、レンダラー + テンプレート選択） |
| **6** | レイアウトレビュー | `06_layout_review.md`（レンダリング前の 構造 / 品質 / ブランドゲート） |
| **7** | レンダリングログ | `07_render_log.md`（DOCX/HTML 生成、判断を記録、PDF を書き出し） |
| **8** | PDF QA | `08_pdf_qa.md`（pdfinfo / pdffonts + ビジュアルチェック、ゲート結果、最終パス） |

**パイプラインの透明性**：すべての判断はそのステップファイルに記録（追跡可能）、ユーザーは任意のステップで一時停止・レビュー・修正可能（監査可能）、Brain は重要な選択をその場で説明（説明可能）、反復は安価（低コストなロールバック）。

## トークンモデル

各企業はレンダリング前にトークンファイルを取得します。JSON または YAML を使用。カラー、フォント、サイズ、スペーシングをテンプレートにハードコードしないでください。

```yaml
company:
  legal_name: "Acme Holdings, Inc."   # 例のみ —— 対象企業に置き換え
  ticker: "0000"
  market: "Tokyo Stock Exchange Growth"
  brand_name: "Acme"

brand:
  primary: "#c0392b"        # 例のブランドパレット —— 企業の実トークンに置き換え
  primary_dark: "#922b21"
  text: "#242424"
  background: "#ffffff"
  border: "#d9d9d9"

language:
  ja_font: "Hiragino Sans"
  zh_font: "PingFang SC"
  latin_font: "Aptos"

docx:
  page_size: "A4"
  body_pt: 12
  line_spacing: 1.18
  chapter_page_break: true

slides:
  canvas_px: [1920, 1080]
  base_font_px: 20
```

ルール：

- トークンが追加のセマンティックカラーを定義しない限り、企業の主色を唯一の機能アクセントとして使う。
- ブランドが必要としない場合、青/緑/オレンジの機能色を避ける。
- 階層はウェイト、スペーシング、抑制されたテキストで表現し、制御不能なフォントサイズでは表現しない。

## 品質ゲート

Step 6（レイアウトレビュー）と Step 8（PDF QA）の背後にある具体的なチェック。最終納品前に実行します。

- 出力が要求されたフォルダに存在し、DOCX が修復警告なしで開く。
- PDF が最終 DOCX/HTML ソースから書き出され、フォントが読みやすく言語に適している。
- 正式 Word ドキュメントの本文は 12pt（上書きされない限り）、必要に応じて章が新しいページから始まる。
- 目次の配置が正しく、テーブルがページ余白をはみ出さず、図が崩れておらず、不安定な Word の図形矢印で作られていない。
- 企業ブランドが赤/グレーのとき、意図しない青/緑/オレンジが出ない。
- 日中分割ファイルが正しい言語を含む。
- HTML デックでは、ブラウザのスクリーンショットと PDF 書き出しの両方がはみ出さない 16:9 スライドを示す。
- **数値忠実度が成立**：すべての数値、単位、通貨、会計期間がソースと一致、ギャップは `[DATA_GAP]`、未検証の法律/税務記述は草案としてマーク。

```bash
pdfinfo "/path/to/output.pdf"
pdffonts "/path/to/output.pdf"
```

## 納品規約

ユーザーが別の宛先を指定しない限り：

- 最終ファイルは `~/Downloads`（macOS/Linux）または `%USERPROFILE%\Downloads`（Windows）へ。
- 出力ファイル名はソースファイル名に近づけ、`_精修版`、`_日本語版`、`_中文版`、`_CFO Proposal` などの明確なサフィックスを付ける。
- 明示的に要求されない限り、ソースファイルを上書きしない。

## 由来

このスキルは [EIP（Explain In Picture）](https://github.com/jasonhnd/eip) プロジェクトから派生しています。EIP は AI 駆動のビジュアルドキュメント生成 Web アプリケーション（Next.js 16 + React 19 + Tailwind CSS 4）であり、Engine 1.0 方法論を蓄積しました：3 段階パイプライン、ビジュアルテンプレートスケルトン、コンテンツ戦略、分類エンジン、深度可視化ルール、S/M/L/XL サイズ制御。

make-doc-skill v4 はその Brain -> Router -> Canvas インテリジェンスを引き継ぎ、企業ドキュメント —— 正式 Word/PDF 取締役会資料、IR/CFO 提案、日中バイリンガル成果物 —— に向け直しつつ、EIP 由来の HTML 機構をオプションの出力モードとして保持しています。
